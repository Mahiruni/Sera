# Signed-in workspace release

The career overview at `/dashboard` uses real account activity, with recent applications, saved roles, application messages, exact totals and a transparent profile setup checklist. An employer's preferred journey opens `/employer` by default; `/dashboard?view=candidate` explicitly opens their career view. Both views remain available to a verified user, and journey preferences grant no additional data permissions or employer-verification status.

The hiring overview shows only the current user's jobs and applications to those jobs. Postings have open/closed filters and pagination (eight items per page); incoming applications have independent pagination. Posting status actions preserve both pages and the current filter. Messages are the latest three message records, with a total message count; these are not unread or conversation counts. No notifications, recommendations or live activity are fabricated. The career overview previews six applications and three saved roles, linking to the existing detail lists.

Queries run in parallel through the authenticated Supabase client, with explicit account scope and the existing RLS policies. No new grants, schema changes, security-definer functions or service-role queries are needed. Private files remain owner-only. Missing data or a failed query shows an unavailable state rather than an invented zero. Profile completeness explains each included field and does not require a phone number or CV for employers.

The information footer is omitted from signed-in workspace pages. The curved dock, active teal icon/text and icon-only animation remain unchanged. Workspace navigation, stage labels, loading states, mobile layouts and footer clearance are shared across account routes. The drawer presents real account navigation rather than local demo-role controls while signed in.

Validation: 22 unit tests, lint and production build pass. Authenticated API query checks verify employer totals, nested message ownership, career/hiring separation and anonymous exclusion of the closed QA posting. Production route checks and fixture cleanup are part of the release verification. Browser visual verification requires a signed-in browser; source-level responsive and reduced-motion rules are not a claim of testing on every device. The pre-existing leaked-password-protection advisory remains unchanged.
